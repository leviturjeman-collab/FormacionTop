# Fases de la formacion

Esta carpeta reorganiza toda la academia por fases. La estructura anterior por carpetas, modulos, laboratorios y proyectos sigue siendo util, pero no siempre responde a la pregunta mas importante de un alumno: "en que momento estoy y que tengo que hacer ahora". Las fases sirven para convertir la boveda en un camino de aprendizaje y aplicacion.

## Por que fases y no solo modulos

Los modulos ordenan el contenido por tema: ChatGPT, Codex, Claude, Gemini, GitHub Skills, n8n, agentes, produccion. Las fases ordenan el contenido por madurez del alumno. Esto es distinto. Una persona puede leer una leccion sobre n8n en fase de aprendizaje, usar n8n para su trabajo en fase de aplicacion, construir un workflow real en fase de proyectos, convertirlo en agente en fase de automatizacion y prepararlo para produccion en fase final.

Por eso las fases no sustituyen los modulos. Los atraviesan. Cada fase responde a una pregunta:

- Fase 00: que quiero conseguir y que nivel tengo.
- Fase 01: que necesito entender.
- Fase 02: como aplico esto a mi trabajo e ideas.
- Fase 03: como construyo algo concreto.
- Fase 04: como automatizo y creo sistemas con agentes.
- Fase 05: como lo convierto en algo presentable, seguro y mantenible.

## Fase 00 - Orientacion y diagnostico

Esta fase prepara al alumno. No se trata de estudiar mucho, sino de situarse. La persona identifica su perfil, su sistema operativo, sus objetivos, sus herramientas disponibles y sus restricciones. Tambien hace una evaluacion diagnostica.

Esta fase une workflows, tools, skills, MCP, memory, RAG, HITL y agentes. La fase final convierte lo construido en algo defendible, mantenible y presentable. Entran seguridad, secretos, permisos, logs, coste, evals, rollback, defensa final y portfolio. No todo alumno tiene que desplegar a produccion real, pero si debe entender que cambia cuando un sistema toca usuarios, datos o dinero.

## Como usar las fases para impartir

Para un curso corto, usa fases 00, 01 y 02. Para una formacion profesional, usa las seis. Para un bootcamp tecnico, acelera fase 01 y dedica mas tiempo a fases 03, 04 y 05. Para perfiles no tecnicos, extiende fase 02 y usa proyectos Nivel A o B. Para perfiles tecnicos, introduce antes Codex, GitHub Skills, n8n, MCP y evaluaciones.

## Como evaluar el avance por fases

Cada fase debe cerrarse con una evidencia. En la fase 00, la evidencia es una ruta personal. En la fase 01, una explicacion clara de conceptos. En la fase 02, workflows aplicados al trabajo real. En la fase 03, un proyecto funcional. En la fase 04, una arquitectura automatizada o agentica con controles. En la fase 05, una defensa y un portfolio.

El avance no se mide por horas consumidas. Se mide por capacidad de actuar. Un alumno puede haber visto muchas clases y no estar preparado si no puede explicar que construye, por que lo construye, que necesita, que riesgos tiene y como lo verifica. Las fases obligan a comprobar esa madurez.

## Como adaptar la ruta a perfiles distintos

Un perfil directivo puede necesitar mas fase 02: aplicar IA a decision, documentos, reuniones, reporting y estrategia. Un perfil operativo puede necesitar fase 02 y 04: workflows, n8n y automatizacion. Un perfil tecnico puede avanzar antes a fase 03: Codex, Claude Code, GitHub Skills y proyectos. Un perfil formador puede usar fase 01 y 02 para crear materiales y despues fase 05 para portfolio. Un emprendedor probablemente necesitara todas: entender, aplicar, construir, automatizar y presentar.

La ruta por fases permite personalizar sin romper la estructura. Todos comparten vocabulario, pero no todos necesitan la misma profundidad tecnica desde el primer dia.

## Regla de reentrada

Un alumno puede volver a fases anteriores. Si en fase 04 no entiende permisos, vuelve a fase 01 y glosario. Si en fase 03 no sabe llevar una idea a proyecto, vuelve a fase 02. Si en fase 05 no puede defender riesgos, vuelve a fase 04 y produccion. Esto no es retroceso; es aprendizaje iterativo.

## Clasificacion por ordenador y sistema operativo

Antes de convertir esta nota en una practica, laboratorio, documento o proyecto para otra persona, clasificala segun el ordenador del alumno y el nivel tecnico de ejecucion. Usa estas guias:

- [[../10_GUIAS_WINDOWS_MAC_LINUX/Windows]] para alumnos que trabajen con PowerShell, rutas `C:\...`, OneDrive, Git for Windows, Node.js, Python o Docker Desktop.
- [[../10_GUIAS_WINDOWS_MAC_LINUX/macOS]] para alumnos que trabajen con Terminal/zsh, rutas `/Users/...`, Homebrew, permisos de macOS o Apple Silicon.
- [[../10_GUIAS_WINDOWS_MAC_LINUX/Linux]] para alumnos que trabajen con Bash, rutas `/home/...`, gestores `apt`, `dnf` o `pacman`, permisos, servicios y Docker Engine.
- [[../10_GUIAS_WINDOWS_MAC_LINUX/Compatibilidad_de_proyectos]] para clasificar la practica como Nivel A, B, C, D o E.
- [[../10_GUIAS_WINDOWS_MAC_LINUX/Checklist_entrega_multisistema]] para comprobar que cualquier persona pueda seguirla sin depender de explicaciones orales.

## Criterio de clase inolvidable

Para que esta nota se convierta en una clase que impacte, necesita cinco momentos:

1. Reconocimiento: el alumno ve un problema real suyo.
2. Claridad: entiende el modelo mental.
3. Accion: produce algo pequeño.
4. Tension: algo se rompe.
5. Dominio: lo repara y lo explica.

Sin tension no hay aprendizaje profundo. Sin reparacion no hay confianza. Sin explicacion no hay transferencia.

## Criterio de proyecto inolvidable

Para que un proyecto derivado de esta nota sea memorable, debe tener:

- Nombre claro.
- Resultado visible.
- Dificultad honesta.
- Evidencia.
- Error reparado.
- Mejora respecto a la version inicial.
- Utilidad para alguien real.
- Posibilidad de enseñarse en portfolio.
